# swift-linter

Use this package when you want to run syntax-tree lint rules over a Swift package, the kind of rule a regular expression over source text can't express, either from the `swift-linter` command or from a `Lint.swift` file at the package root. Start from `Lint.run(dependencies:rules:)` in that file, or from `Lint.Run.run(paths:capturing:configuration:)` when you drive the engine from code. The rule and configuration types come from swift-lint, and ready-made rules come from swift-linter-rules.

## Laws

- Nothing is checked by default. With no configuration at the package root, no rules are active.
- The command looks at the first path it is given and takes the first of these it finds there: a `Lint.swift` with a `swift-linter-tools-version:` header in its first 30 lines, a nested `Lint/` package, or a `Lint.swift` without that header, which only loads when `SWIFT_LINTER_PATH` names a swift-linter checkout and fails otherwise. That older form never activates rules. It can only exclude paths and disable rules.
- A `Lint.swift` with the header is built and run as its own package inside `.swift-lint/` in the package root. That directory contains a `.gitignore` that ignores everything in it. The build depends on swift-linter at `SWIFT_LINTER_PATH` if set, otherwise on the published package at branch `main`, or at `SWIFT_LINTER_BRANCH`. Its `Package.resolved` is deleted before every run, so dependencies resolve again each time.
- When `SWIFT_LINTER_RUNNER` or `--local-runner` names a prebuilt runner, a `Lint.swift` whose rules are one bundle that runner bakes, optionally with `.excluding(rules:)`, runs on that runner without building anything. Any other `Lint.swift` is built as usual, except with `--local-runner`, which fails instead.
- Every `.swift` file under each path is linted in path order. Files under `.build`, `.swiftpm`, `.benchmarks`, `DerivedData`, `Carthage`, `Pods` or a `.docc` catalog are skipped, and so is everything inside a nested package, meaning a subdirectory whose `Package.swift` really is a manifest. A path that names a `.swift` file lints only that file. A file that isn't valid UTF-8 stops the run.
- `// swift-linter:disable:next <rule>` suppresses that rule on the next line that has code, skipping blank lines. `// swift-linter:disable:line <rule>` suppresses it on the directive's own line. `// REASON:` comments right after a directive record the reason. A directive only takes effect if the rule allows that kind of directive. Suppressed findings are still reported, separately from the others.
- Errors and warnings count as violations. Notes and remarks are reported as findings but are not violations.
- The run exits with 2 when any rule could not measure a file. Otherwise it exits with 1 under the strict exit policy if any finding is an error, and with 0 under the default advisory policy. A runner also exits with 1 when a rule's own controls fail.
- The default text output is one line per finding, `path:line:column: severity: rule: message`, with the declaration's visibility appended in brackets when known. A one-line summary goes to stderr. SARIF output is version 2.1.0 and reports remarks as notes. The format is chosen with `--format` or `SWIFT_LINTER_FORMAT`, and an unknown value is an error rather than a fallback to text.
- A runner baked with several bundles needs `SWIFT_LINTER_BUNDLE` to name one of them. An unset or unknown bundle, or one that bakes no rules, is an error rather than a clean run. A `--profile` must list exactly the rules the runner bakes for its bundle.
